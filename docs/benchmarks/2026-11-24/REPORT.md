# 本机后端压测报告 · 2026-11-24

本轮未修改业务实现，使用 Release 构建与测试模型，真实访问 MySQL、Redis、ZooKeeper 和 RabbitMQ。没有调用付费模型、没有使用真实简历；数据和账号为随机隔离测试库。测试结束已停止临时进程、清理测试数据库/Redis/MQ 资源，用户原有 50051/8888 服务保持运行。

## 结论

- 单实例在并发 8–128 的短时完整流程测试中约 98–114 次成功流程/秒；并发继续升高主要增加等待。
- 双实例在并发 128 时为 230.4 次成功流程/秒，约为单实例 2.02 倍；p95 从 1107.6ms 降至 553.4ms，会话均衡分配到两个后端。
- 并发 160 出现大量连接重置：单实例完整流程失败 59.7%，双实例 58.4%。不能将这一档吞吐视为可用容量。
- 最大风险是网关的一连接一工作线程模型：128 条空闲 WebSocket 会占满全部 128 个连接名额，导致新 HTTP 请求全部失败。真实网页每个在线用户常驻一个 WebSocket，短时无常驻连接的 128 并发结果不能作为在线用户容量。
- 3670 条已提交报告 outbox 均成功投递并生成异步文档，没有遗漏；本轮不包含 MQ 崩溃/重复投递故障注入，可靠性逻辑由既有集成测试覆盖。

## 环境与口径

Apple M5、10 逻辑 CPU、16 GiB RAM；macOS 本机运行。Apple clang 21.0.0，CMake 4.2.3，Redis 8.8.0，RabbitMQ 4.4.0。代码基线为 0caed4a 加当前未提交的中间件实现。所有压测进程与 MySQL/Redis/MQ/ZooKeeper、压力机和用户其他服务共享资源。

源数据：[results.json](results.json)、[connections.json](connections.json)、[queue-1.json](queue-1.json)、[queue-2.json](queue-2.json)。

一个完整流程 = 创建一题面试 → 提交回答并生成总结/持久化报告 → 查询报告；包括 3 次业务请求。下表的“流程/秒”不是单接口 RPS，也不是真实 LLM tokens/s。

每档逻辑请求数为 max(100, 并发×2)，共 12 档、2008 次 HTTP 流程尝试；每档先执行同数量的原生 C++ gRPC 测试，共 2008 次原生流程且全部成功。HTTP 完整成功 1630 次。失败流程可能已保存报告但尚未成功查询，因此 outbox 总数会高于成功 HTTP 流程总数。

每档重启后端和网关并使用独立 ZooKeeper 注册路径，避免 1000 会话上限和旧临时节点污染测试。账号、数据库在一个拓扑内复用。HTTP 客户端为 Python 标准库线程池，原生客户端为 C++ 多线程。不自动重试业务请求。表中延迟包括失败流程；有错误的档位仅用于展示过载行为。

## 延迟分布与瓶颈线索

单实例并发 128：创建 p95 72.6ms、回答 p95 1063.8ms、报告读取 p95 24.2ms；双实例对应 85.9ms、480.4ms、24.1ms。主要排队发生在回答/报告保存阶段。模型是立即返回的 mock，因此不包含网络模型的生成等待。

代码检查发现报告仓储 Save 用进程级 mutex 包住新建 MySQL 连接与事务；同进程报告保存串行化，与单实例吞吐平台、双实例近两倍增长的表现一致。这是待性能剖析确认的瓶颈线索，并非已完成 CPU/锁 profiling。

SSE 回答首个 DELTA 的 p50 在并发 128 时约 22ms（测试模型）。这只是 mock 数据开始显示的时间，不能推断真实火山模型 TTFT。JSON 完整校验和持久化后才返回最终完成事件。

ps 每 250ms 采样，阶梯测得单个网关/后端的 RSS 最大约 64.5 MiB。CPU 为 ps 的进程累计百分比口径，且短时阶段样本有限，不据此声明 CPU 已饱和或长期无内存增长。

## 常驻 WebSocket 补测

固定单后端，64 个 HTTP 客户端，单份已缓存报告循环读取，每阶段约 6 秒，客户端限速预算上限 100 请求/秒。不是最大读吞吐测试。

| 空闲 WebSocket | 报告请求尝试 | 成功 | 失败率 | 成功请求/秒 |
| --- | --- | --- | --- | --- |
| 0 | 576 | 576 | 0.0% | 95.0 |
| 64 | 588 | 588 | 0.0% | 88.7 |
| 96 | 640 | 571 | 10.8% | 85.8 |
| 128 | 640 | 0 | 100.0% | 0.0 |

64 条 WebSocket + 64 HTTP 客户端无错误；96 条 WebSocket 已出现 10.8% 拒绝；128 条 WebSocket 时新请求 100% 失败。网关超过容量直接关闭 TCP，没有稳定的 HTTP 503/Retry-After。这比单纯增加后端节点更需要优先处理。

另外进行过一轮未限速的 15 秒读取探索，出现客户端 EADDRNOTAVAIL（Can't assign requested address）以及 Redis/MySQL 连接错误。该轮已终止且未计入容量表，系统配置未修改。原因与大量短连接/本机临时端口资源有关，不能把压力机出错解释为后端最大 RPS。之后检查 MySQL/Redis 正常，并用限速补测获得上表。

## RabbitMQ 异步任务积压清理

单实例各档累计 1820 条报告事件：依次启动发布/消费 worker，19.20 秒清空，report_documents=1820；双实例累计 1850 条，19.09 秒清空，report_documents=1850。publisher/consumer 退出码均为 0。

这里是“先全量发布、再全量消费”的总耗时，约 95–97 条文档/秒，仅代表当前数据库/worker实现的积压清理速度，不能作为 RabbitMQ broker 极限吞吐。worker 没有与 API 压测并行运行，不代表混合业务运行时延迟。

## 建议优先级

1. 网关改异步 I/O/连接与业务线程分离，空闲 WebSocket 不占一个阻塞工作线程；增加明确的容量拒绝响应。
2. MySQL 连接池、缩小仓储锁范围，让不同报告的事务并发；Redis 复用连接，减少短连接和临时端口消耗。
3. 增加进行中会话过期清理，目前每实例 1000 条内存会话上限会在长时间运行后触发；本轮为隔离它而按档重启。
4. 完成后做 10–30 分钟稳态、长 SSE 与真实模型延迟模拟、MQ 同时运行，以及独立压力机/云端测试；再确定生产容量。

本报告是短时本机阶梯与边界测试，不是长期稳定性、云服务器容量或真实 LLM 并发额度结论。本轮只新增压测工具和报告，没有自动优化或改变服务实现。
